# Pigeon Control API v1

Status: draft v0.1 (2026-10-14). **Phase 1 implemented** in `pigeon/control_api/`: `/hello`, `/claim`, `/device`, `/capabilities`, `/status`, `/events`, `/search/*`, `/controllers*`. Everything else is still design. `poster_url` fields and `/media/poster` arrive later. Companion to [PIGEON_COMPANION_ROADMAP.md](PIGEON_COMPANION_ROADMAP.md).
The Control API is how the **Pigeon Remote** iOS app discovers and configures PigeonOS devices (Pigeon Clock, Pigeon Marquee). The device is the source of truth; there is no cloud.

## Decisions this spec assumes

These resolve the roadmap's open decisions with its recommendations. Changing one means revising the sections noted.

| # | Decision | Choice | Where it matters |
|---|---|---|---|
| 1 | Marquee board | Pi Zero 2 W is the floor, validated in roadmap Phase 3 | `profile.limits` |
| 2 | Headless provisioning | Setup hotspot (not BLE) | §3 |
| 3 | Transport security | HTTPS with a self-signed certificate pinned by SHA-256 fingerprint; the plain port only serves `/hello` | §2.3 |
| 4 | Naming | `pigeon` package and `PigeonOS` unchanged; `product` field distinguishes devices | §4 |
| 5 | Multi-device | Per-device API only; the app fans out to several devices itself | §1 |

## 1. Conventions

- **Base URL:** `https://<host>:8781/api/v1` (TLS port `8781`, `PIGEON_CONTROL_TLS_PORT`), certificate pinned per §2.3. A plain `http://<host>:8780/api/v1` listener remains for `GET /hello`, `POST /pair/start` and `POST /pair/cancel` only; everything else there returns `426 tls_required`. Host comes from mDNS (§2.1).
- **Format:** JSON, UTF-8. `Content-Type: application/json` on bodies. Timestamps are RFC 3339 UTC strings.
- **Versioning:** the path carries the major version. Within v1, changes are **additive only**: new endpoints, new optional fields, new enum values. Clients must ignore unknown fields and tolerate unknown enum values.
- **Auth:** `Authorization: Bearer <token>` on everything except endpoints marked *open*.
- **Methods:** `GET` reads, `PUT` replaces, `PATCH` merges (JSON Merge Patch, RFC 7396), `POST` triggers an action or creates, `DELETE` removes. `PUT` and `DELETE` are idempotent.
- **Long operations** (Wi-Fi scan, discovery, pairing, update) return `202 Accepted` with a `session` object; progress arrives over `GET /events` and the final state is readable at the session URL.
- **Single device:** every request targets exactly one device. Grouped actions ("send this title to every device in the room") are the app's job in v1.
- **Names are display strings.** IDs (`device.id`, `location.id`, `player.id`) are opaque and stable; never parse them.

### 1.1 Errors

Every non-2xx response has this body:

```json
{ "error": { "code": "wifi_join_failed", "message": "Password rejected by the network.", "details": {} } }
```

| HTTP | `code` | Meaning |
|---|---|---|
| 400 | `bad_request` | Malformed JSON or failed validation (`details.fields` lists offenders) |
| 401 | `unauthorized` | Missing or invalid token |
| 403 | `not_claimed` / `already_claimed` | Claim state does not allow this call |
| 404 | `not_found` | Unknown resource |
| 409 | `conflict` | State conflict, e.g. a pairing session already running |
| 422 | `unsupported` | Valid request, device lacks the capability (§4.2) |
| 429 | `rate_limited` | Too many failed claims or PIN attempts; `Retry-After` set |
| 503 | `busy` | Device is mid-operation (updating, restarting) |

Operation-specific codes (`wifi_join_failed`, `pin_required`, `pin_rejected`, `device_unreachable`) are listed with their endpoints.

## 2. Discovery, claim and auth

### 2.1 Discovery (mDNS / Bonjour)

Each device advertises `_pigeon._tcp` on its API port.

| TXT key | Example | Notes |
|---|---|---|
| `id` | `pgn-7f3a91` | Same as `device.id` |
| `name` | `Theater Clock` | Display name |
| `product` | `clock` \| `marquee` | |
| `api` | `1` | Highest supported major version |
| `ver` | `0.12.11` | PigeonOS version |
| `claimed` | `0` \| `1` | Whether a controller owns it |

The TXT record is a hint. `GET /hello` is authoritative.

### 2.2 `GET /hello` *(open)*

```json
{
  "id": "pgn-7f3a91",
  "name": "Theater Clock",
  "product": "clock",
  "api": 1,
  "version": "0.12.11",
  "claimed": false,
  "setup_mode": false
}
```

### 2.3 Claiming a device

A device is **unclaimed** until a controller claims it. The claim proves physical presence: the device shows a 6-digit **pairing code** on its own screen (Clock: on the display; Marquee: on its HDMI output).

`POST /claim` *(open while unclaimed; 403 `already_claimed` otherwise)*

```json
// request
{ "code": "482913", "controller": { "name": "Jason's iPhone", "id": "<uuid generated by the app>" } }
// 200 response
{ "token": "pgt_Zk3...", "device": { "id": "pgn-7f3a91", "name": "Theater Clock" } }
```

**Showing the code on the screen (like the Apple TV PIN).** When the user picks a device in the app, the app first calls `POST /pair/start` *(open; works even when already claimed, since the on-screen code is the proof of presence)*. The device then draws the code **full screen** until the claim succeeds, `POST /pair/cancel` *(open, `204`)* is called, or 120 seconds pass. The response is `{ "expires_in_s": 120 }` and never contains the code: seeing the screen is the proof of presence. Anyone on the LAN can trigger or dismiss the prompt, which is a nuisance, not a way in, since the code is still required to claim.

- The token is a 256-bit random value, stored in the iOS Keychain. The device stores only a hash.
- The code is regenerated on every boot and after 5 failed attempts; failures are rate-limited (`429`).
- Multiple controllers may hold tokens (a household with two phones). `POST /claim` while claimed is refused; extra controllers are added by an existing controller via `POST /controllers/invite` (returns a fresh code valid 5 minutes).
- Tokens never appear in URLs or query strings.
- `GET /controllers` lists controllers; `DELETE /controllers/{id}` revokes one. A physical factory reset (`POST /factory-reset` with a fresh on-screen code) returns the device to unclaimed.

**Transport security.** The device generates a self-signed EC P-256 certificate on first start (`control_api_tls_cert.pem` / `control_api_tls_key.pem` in the state directory, key mode `0600`, valid 10 years, regenerated if unreadable or within 30 days of expiry). No CA is involved: clients pin it.

- `GET /hello` (plain or TLS) and the mDNS TXT record (`tlsport`, `fp`) carry `tls: { "port": 8781, "fingerprint_sha256": "<64 hex>" }`, the SHA-256 of the certificate's DER bytes.
- A client reads the fingerprint **before the first claim**, then connects to the TLS port and accepts only a certificate whose SHA-256 matches (hostname and chain checks are skipped; the pin replaces them). It stores the fingerprint alongside the token and keeps enforcing it. A changed fingerprint means a different device, a factory reset or an attack: surface it, do not silently re-trust.
- `/claim`, the token and every other request go over TLS only. The plain listener answers `426 tls_required` (with the `tls` details) and ignores any request that carries an `Authorization` header.
- Trust on first use: an attacker who is an active man-in-the-middle during the very first `GET /hello` can substitute their own fingerprint. The on-screen pairing code is still needed to claim, so they cannot get a token from the real device; showing the fingerprint's first characters on the device screen for the user to compare would close the gap (not built yet).
- Legacy clients: `PIGEON_CONTROL_ALLOW_PLAIN=1` serves the full API over plain HTTP again (tokens in the clear; only until the companion app ships pinning). `PIGEON_CONTROL_TLS=0` disables TLS and logs a warning. If TLS is wanted but no certificate can be created (no `openssl` command and no `cryptography` package), the API does not start rather than falling back to plain HTTP.

**Connection limits.** At most 24 concurrent connections, 8 per client address; extras get `503` (`Retry-After: 2`) without costing a thread. Every socket read or write has a 10 s timeout (TLS handshake, headers, body, idle keep-alive, a stalled event-stream reader), and a request must be fully received within 15 s. Clients should reuse connections and keep only a few open besides `GET /events`.

## 3. First-boot provisioning (setup hotspot)

For an unconfigured, headless device with no network:

1. Device has no saved Wi-Fi and no link → enters **setup mode**: starts an open or WPA2 access point `Pigeon-XXXX` (XXXX = last digits of `id`); HDMI shows the SSID, pairing code and "Open the Pigeon app".
2. App joins the hotspot (`NEHotspotConfiguration`). The device is reachable at `http://10.42.0.1:8780`.
3. App claims (§2.3), then calls `GET /wifi/scan` and `PUT /wifi`.
4. Device tears down the AP and joins the network. On success it advertises over mDNS; the app rejoins the home network and finds it.

While in setup mode: `GET /hello` returns `"setup_mode": true`, only `/hello`, `/claim`, `/wifi/*`, `/device` and `/status` are served, and the AP shuts down after 15 minutes idle (the device retries the saved network or re-enters setup).

If the join fails, the device **re-enters setup mode** rather than going silent, and reports `wifi.state = "failed"` with `last_error` so the app can show the reason after reconnecting to the hotspot.

## 5. Status and events

### 5.1 `GET /status`

```json
{
  "state": "playing",
  "now_playing": {
    "title": "Blade Runner 2049",
    "kind": "movie",
    "source": "detected",
    "tmdb_id": 335984,
    "app": "Netflix",
    "position_s": 1822,
    "duration_s": 9840,
    "poster_url": "/api/v1/media/poster/335984"
  },
  "manual_search": { "active": false },
  "wifi": { "state": "connected", "ssid": "HomeNet", "signal": 78 },
  "players": [ { "id": "ply-1", "name": "Living Room Apple TV", "paired": true, "reachable": true } ],
  "receivers": [ { "id": "rcv-1", "name": "Denon AVR-X", "paired": true, "reachable": true } ]
}
```

`state` is one of `idle`, `playing`, `paused`, `manual`, `updating`, `setup`. `now_playing.source` is `detected` or `manual`; mirrors the app's rule that a detected title wins over a manual one.

### 5.2 `GET /events` (Server-Sent Events)

`Accept: text/event-stream`. The stream starts with a `snapshot` event holding the full `/status` body, then deltas. Events are named; `data` is JSON. Clients reconnect with `Last-Event-ID` and receive a fresh `snapshot`.

| Event | Payload |
|---|---|
| `snapshot` | full status |
| `now_playing` | now-playing object or `null` |
| `manual_search` | `{ active, entry }` |
| `wifi` | wifi object |
| `session` | session object (§6.7) |
| `settings` | `{ changed: ["id", ...] }` |
| `device` | `{ name?, claimed? }` |

A `: keepalive` comment is sent every 15 s.

### 5.3 `GET /media/poster/{tmdb_id}` *(not in Phase 1)*

Returns the cached poster image (`image/jpeg`) for the current title, size `w500`. 404 if not cached. Lets the app show artwork without its own TMDb key.

## 6. Resources

### 6.1 Search *(capability `manual_search`; the app's primary feature)*

Wraps `pigeon/manual_search.py`. Suggestion lookups are debounced and off-thread on the device.

`GET /search/suggest?q=<text>&limit=3&logos=1&kind=movie&year=1977`

```json
{
  "query": "blade run",
  "results": [
    { "tmdb_id": 335984, "kind": "movie", "title": "Blade Runner 2049", "year": 2017,
      "poster_url": "https://image.tmdb.org/t/p/w185/….jpg",
      "logo_url": "https://image.tmdb.org/t/p/w300/….png" },
    { "tmdb_id": 78,     "kind": "movie", "title": "Blade Runner",      "year": 1982,
      "poster_url": "https://image.tmdb.org/t/p/w185/….jpg" }
  ]
}
```

Query must be ≥ 2 characters (`400` otherwise). `limit` 1–12, default 3 (the device caps its TMDb fetch at 12). `poster_url` is included whenever TMDb has a poster. `logo_url` (the title-treatment logo, English only) is included only with `logos=1`, because it costs the device one extra TMDb lookup per result (about a second for 12); a title with no English logo simply has no `logo_url`. Clients load both images straight from TMDb. Both fields are optional additions. `kind` (`movie` or `tv`) and `year` (four digits) narrow the hits; anything else is `400`. The call blocks until TMDb answers, so there is no `pending` state; clients debounce.

`GET /search/current` → `{ "active": true, "entry": { "title": "...", "kind": "movie", "tmdb_id": 335984 } }` or `{ "active": false }`.

`PUT /search/current`: pin a title.

```json
{ "title": "Blade Runner 2049", "kind": "movie", "tmdb_id": 335984, "year": "2017" }
```

`title` is required; `kind` is `movie` or `tv`; `tmdb_id` optional but preferred; `year` optional and improves the on-device TMDb match. Persists on the device until cleared.

`DELETE /search/current`: clears the pinned title. `204`.

### 6.1a Now playing: inspect and correct the match *(capability `now_playing_override`)*

Shows the metadata that fed the TMDb query and lets the user correct it when Pigeon picked the wrong title. A correction is **remembered**: it is stored on the device against the title keys the content was detected under (the title, series, episode and Apple TV search text, normalized), so the same wrongly-detected title is corrected every time it plays, and after a restart. It applies whenever the detected metadata shares a key with a stored correction, so Apple TV alternating between the show name and an episode title does not lose it. It never applies to different content. `DELETE` forgets it.

`GET /now-playing/detail`

```json
{
  "content_active": true,
  "app": "Disney+",
  "inputs": [
    { "key": "title", "label": "Title", "value": "The Final Show", "editable": true },
    { "key": "series_name", "label": "Series", "value": "", "editable": true },
    { "key": "episode_title", "label": "Episode title", "value": "", "editable": true },
    { "key": "query", "label": "Apple TV search text", "value": "The Final Show", "editable": true },
    { "key": "app_name", "label": "App", "value": "Disney+", "editable": false }
  ],
  "query": {
    "apple_tv": "The Final Show",
    "resolved": "The Final Show",
    "candidates": ["The Final Show"],
    "searched": "The Final Show",
    "prefer": "auto",
    "in_flight": false
  },
  "match": { "title": "Taylor Swift | The Eras Tour", "kind": "movie", "tmdb_id": 1114513,
             "year": "2023", "outcome": "matched", "forced": false },
  "override": { "active": false }
}
```

`inputs` lists the metadata fields the query is built from, in display order; only `editable` ones may be sent back. `match` is `null` until a title has been matched.

`POST /now-playing/preview` takes `{ "fields": {...}, "year": "2023" }` and returns `{ "query", "candidates": [{tmdb_id, kind, title, year}] }`: the query the edits would produce and TMDb's top results for it. Nothing is applied.

`PUT /now-playing/override` applies a correction and re-runs the match. Send either edited fields:

```json
{ "fields": { "title": "Taylor Swift The Eras Tour" }, "year": "2023", "kind": "movie" }
```

or a hand-picked TMDb title (forces that exact id, regardless of how the text search would rank):

```json
{ "pick": { "title": "Taylor Swift: The Eras Tour", "kind": "movie", "tmdb_id": 1114513, "year": "2023" } }
```

`kind` is `auto`, `movie` or `tv`. `400` when nothing would change, the title is empty, or the id is invalid. The response is the new detail body.

`DELETE /now-playing/override` removes the correction and goes back to what was detected. Returns the detail body.

A **location** groups saved devices, Wi-Fi and room name, mirroring the v2 location model in `pigeon/app_state.py`.

|---|---|
| `GET /locations` | List all locations; `current` marks the active one |
| `POST /locations` | `{ "name": "Lake House" }` → `201` location |
| `PATCH /locations/{id}` | Rename |
| `DELETE /locations/{id}` | Delete (`409` if it is the only one) |
| `PUT /location/current` | `{ "id": "loc-2" }` switch active location |
| `GET /location/room` / `PUT /location/room` | `{ "room": "Theater" }` for the current location |

### 6.3a Rooms and Pigeon-page settings *(capabilities `rooms`, `pigeon_settings`)* — implemented

These mirror what `settings_main` and `settings_pigeon` offer on the device. A **room** is one of three fixed slots (the same three the screens show); players, receivers and Wi-Fi belong to a room. This supersedes the more general `/locations` sketch in 6.3 for the clock product.

`GET /rooms`

```json
{
  "current": "d0dd6e66ac6d4d47a0ab23ccec16beda",
  "rooms": [
    { "id": "d0dd6e66...", "slot": 1, "name": "Theater", "current": true },
    { "id": "d433b0...",   "slot": 2, "name": "ROOM 2",  "current": false },
    { "id": "ffc0db...",   "slot": 3, "name": "ROOM 3",  "current": false }
  ],
  "presets": ["Living room", "Bedroom", "Office", "Kitchen", "Basement", "Theater"]
}
```

`PUT /rooms/current` with `{ "id": "..." }` switches room. The device reloads that room's players, receivers and Wi-Fi exactly as the on-screen switch does. `404` for an unknown id.

`PATCH /rooms/{id}` with `{ "name": "Theater" }` renames (1–24 characters). Both return the `GET /rooms` body.

`GET /pigeon-settings`

```json
{
  "version": "0.12.16",
  "zip": "21710",
  "timezone": "America/New_York",
  "timezone_choices": ["America/New_York", "America/Chicago"],
  "options": { "time_format": "12", "temp_format": "f", "color_format": "color",
               "zone4_mode": "info", "clock_format": "digital" },
  "option_values": { "time_format": ["12", "24"], "temp_format": ["f", "c"],
                     "color_format": ["color", "dark"], "zone4_mode": ["info", "visualizer"],
                     "clock_format": ["digital", "analog"] },
  "ui_color": "blue",
  "ui_color_choices": ["blue", "green", "yellow", "pink", "red"]
}
```

`PATCH /pigeon-settings` accepts any subset of `zip` (5 digits), `timezone` (one of `timezone_choices`), `options` (a map of option → allowed value) and `ui_color` (`orange`, `grey` and `white` are no longer listed in `ui_color_choices` but are still accepted). Validation is all-or-nothing: on `400` nothing is changed and `error.details.fields` names the offenders (`options.temp_format`, `zip`, ...). Setting `zip` also looks the timezone up in the background, so re-read after a few seconds. The response is the new `GET` body. On the device the on-screen settings reload immediately.

### 6.3c Restart, update, TMDb refresh, pairing scan — implemented

| Method & path | Capability | Behavior |
|---|---|---|
| `POST /device/restart` | `restart` | `202 {"state":"restarting"}`; relaunches Pigeon (systemd on the Pi). `503` while an update installs. |
| `POST /device/reset` | `factory_reset` | `202 {"state":"resetting"}`; same as RESET on the Pigeon page: settings, theme, location, rooms and paired players/receivers go back to defaults. Controllers stay paired. `503` while an update installs. |
| `GET /update` | `update` | Checks GitHub now: `{local_version, remote_version, update_available, error, applying}`. |
| `POST /update` | `update` | `202 {"state":"updating"}`; installs the newest version, then restarts. `409` if already installing. |
| `POST /now-playing/refresh` | `tmdb_refresh` | Re-runs the TMDb lookup for what is playing (forced). Returns the `/now-playing/detail` body; `409` if nothing is playing. |
| `POST /rooms/{id}/pairing` | `pairing_player` / `pairing_receiver` | `{"kind":"player"\|"audio"}`: switches to that room and starts the device's on-screen search; the user finishes pairing on the Pigeon. `202`. |

### 6.3b Display brightness *(capability `display_brightness`)* — implemented

`GET /display` returns `{ "brightness": 80, "min": 10, "max": 100, "mode": "software" }`. `PATCH /display` with `{ "brightness": 60 }` sets it (an integer from `min` to `max`; `400` otherwise, nothing changed) and returns the same body. The on-screen picture follows immediately and the level is saved across restarts.

`mode` says how the dimming is done. `backlight` means the panel exposes `/sys/class/backlight/*` and the device writes the hardware level, which also saves power. `software` means a gain is applied to every frame before it reaches the screen (HDMI monitors). If a hardware write is refused the device falls back to `software` rather than failing. The floor is 10 % so a stray slider cannot leave the screen unreadable.

### 6.4 Wi-Fi *(capability `wifi`)*

| Method & path | Purpose |
|---|---|
| `GET /wifi` | Current state |
| `POST /wifi/scan` | `202` → session; results arrive as `wifi_scan` session result |
| `PUT /wifi` | Set network for the **current location** and join it |
| `DELETE /wifi` | Forget the saved network for the current location |

```json
// PUT /wifi request
{ "ssid": "HomeNet", "password": "••••••••" }
// 202 response
{ "session": { "id": "ses-91", "kind": "wifi_join", "state": "running" } }
```

Join errors: `wifi_join_failed` (`details.reason`: `bad_password`, `not_found`, `timeout`). A successful join on a device being configured over its own hotspot ends the connection that issued it; the app must follow §3 step 4.

Same shape as players under `/discovery/receivers`, `/receivers`. Receivers are AV receivers (e.g. Denon); volume and power are device-handled, not exposed in v1.

### 6.7 Sessions (long operations)

```json
{
  "id": "ses-91",
  "kind": "player_pairing",
  "state": "needs_input",
  "step": "airplay_pin",
  "prompt": "Enter the PIN shown on your Apple TV.",
  "result": null,
  "error": null,
  "updated": "2026-10-14T18:22:03Z"
}
```

| Field | Values |
|---|---|
| `kind` | `wifi_scan`, `wifi_join`, `discovery`, `player_pairing`, `receiver_pairing`, `update` |
| `state` | `running`, `needs_input`, `succeeded`, `failed`, `cancelled` |

`GET /sessions/{id}` reads it, `DELETE /sessions/{id}` cancels it. Only one session per `kind` may run at a time (`409 conflict`).

**Pairing flow** (player; the receiver flow is the same):

1. `POST /players` → `202` `{ session }` in state `running`.
2. If the player needs a PIN, state becomes `needs_input`, `step: "remote_pin"` (then `"airplay_pin"` for Apple TVs, which pair twice).
3. `POST /sessions/{id}/input` with `{ "pin": "1234" }`. Wrong PIN → session stays `needs_input` with `error.code = "pin_rejected"`; up to 3 attempts, then `failed`.
4. `succeeded` carries `result: { "player": { ... } }`; `failed` carries `error` (`device_unreachable`, `pin_rejected`, `pairing_unsupported`).

This session contract is the target for the `core/pairing.py` state-machine extraction (roadmap Phase 4).

### 6.8 Settings and schema *(roadmap Phase 5)*

`GET /settings/schema` returns the registry; `GET /settings` the values; `PATCH /settings` changes them.

```json
// GET /settings/schema
{
  "version": 3,
  "groups": [ { "id": "display", "label": "Display", "capability": null } ],
  "items": [
    {
      "id": "view_one.layout",
      "group": "display",
      "label": "Layout",
      "type": "enum",
      "options": [ { "value": "full", "label": "Full" }, { "value": "simple", "label": "Simple" }, { "value": "poster", "label": "Poster" } ],
      "default": "full",
      "capability": "now_playing",
      "restart_required": false
    }
  ]
}
```

| Field | Notes |
|---|---|
| `type` | `bool`, `int`, `float`, `string`, `enum`, `color` |
| `min` / `max` / `step` | Numeric limits |
| `capability` | Hidden when the device lacks it (e.g. `viz`) |
| `restart_required` | App prompts for `POST /restart` |
| `version` | Bumped when the schema changes; the app caches by version |

`PATCH /settings` takes a flat `{ "id": value }` map, validates each against the schema and applies atomically. `400 bad_request` with `details.fields` rejects the whole patch. Unknown ids are an error, not ignored.

## 8. Implementation notes

- **Where it runs:** a thread in the existing PigeonOS process (`pigeon/control_api/`), started behind a flag, using stdlib `ThreadingHTTPServer` as `pigeon_report_server.py` does. The API calls the same `app_state` and `manual_search` functions the UI uses; it never edits the state file directly.
- **UI thread safety:** anything that touches Tk (today: pairing, settings widgets) must be marshalled onto the UI thread or, preferably, extracted into UI-free functions first. Search, Wi-Fi, clock and location need no Tk.
- **Limits:** request bodies ≤ 64 KB; at most 4 concurrent SSE streams (Zero 2 W budget).
- **Testing:** the spec's endpoint index becomes a contract test (one test per row) in `pigeonSystem/tests/`, alongside the existing `test_manual_search.py` and `test_app_state.py`.

## 9. Not covered in v1

Marquee signage content (poster rotation, schedules), receiver volume/power control, remote (off-LAN) access, HTTPS, firmware/OS-level updates beyond `/update/*`, and grouped multi-device commands.
